## 3. Стандарты — сверка порогов

Первоисточник — **официальное предисловие IEC 62676-4:2025** (redline-превью IEC, издатель VDE). В его перечне существенных технических изменений, п. c), сказано:
> «upgrade of previous MDORII system with 6 pixel densities (12,5; 25; 62,5; 125; 250; 1 000 pixels/meter) into new O2DCPVS system with 7 pixel densities (20; 40; 80; 125; 250; 500; 1 500 pixels/meter)»

Издание: IEC 62676-4:2025, ed. 2.0, опубликовано 09.10.2025, «cancels and replaces the first edition published in 2014» (IEC webstore, publication 83425).

Названия уровней (полного текста стандарта нет; названия совпадают в трёх независимых вторичных источниках):

| Профиль | Код | Название (EN) | px/m | Источник названий |
|---|---|---|---:|---|
| 2014 MDORII | monitor | Monitor | 12.5 | Axis whitepaper «Quality with a purpose» (таблица по IEC 62676-4) |
| | detect | Detect | 25 | Axis (2014), предисловие IEC |
| | observe | Observe | 62.5 | Предисловие IEC: 62,5 (у Axis округлено до 63) |
| | recognize | Recognize | 125 | Axis, предисловие IEC |
| | identify | Identify | 250 | Axis, предисловие IEC |
| | inspect | Inspect | 1000 | Axis «Quality with a purpose», предисловие IEC |
| 2025 O2DCPVS | overview | Overview | 20 | Axis 2025, Hikvision (SourceSecurity, 15.01.2026), euro-security.de (27.02.2026) |
| | outline | Outline | 40 | те же |
| | discern | Discern | 80 | те же |
| | perceive | Perceive | 125 | те же |
| | characterize | Characterise / Characterize | 250 | те же; у euro-security — британское написание |
| | validate | Validate | 500 | те же |
| | scrutinize | Scrutinise / Scrutinize | 1500 | те же |

Подтверждённые уточнения к ТЗ:
1. **В 2014 году уровней шесть (MDORII), а не четыре.** ТЗ §5 само это допускает. Решение: в базовом виде показывать DORI (4 уровня), в экспертном — все 6.
2. Деление 2025 на группы: LPDO = Overview, Outline, Discern; HPDO = Perceive … Scrutinize (Axis 2025).
3. Порядок букв в аббревиатуре O2DCPVS не совпадает с порядком порогов: в источниках Perceive = 125, Characterise = 250. Порог привязан к названию по таблицам источников, а не по аббревиатуре. **Сверить с полным текстом п. 6.7, если он появится.**
4. Ограничения, которые указывают все источники: пороги — упрощённая модель для изображения, которое оценивает человек. На аналитику и тепловизоры они не переносятся, на результат влияют свет, оптика, сжатие и экран оператора.
5. Названия уровней на пяти языках — собственные формулировки, в скобках английский термин. Текст стандарта на сайт не переносится.
6. Ссылки на Axis и других производителей — только в этом документе и в `03-IEC-PROFILES-AND-SOURCES.md`, на сайт не выводятся (правило «никаких чужих сайтов»).

Контрольный пример ТЗ сверен вручную: `2·atan(5.4/5.6)` = 87,917° (в ТЗ — «≈ 87,9»); `10·5.4/2.8` = 19,2857 м; `2560/19.2857` = 132,74 px/m. Цифры ТЗ верны. Окончательно проверяет тест.

Почти всё — артикулы с объективом (`ds-2cd1343g2-liu 2.8mm`), то есть спрос на карточки товаров. Из общих запросов: `obyektiv nima` (22 показа), `ip камера 2.8 мм` (17 + 14) |

| Планировщик, «dori» = 2 400/мес | **Ложный сигнал:** по-узбекски *dori* — «лекарство». Брать нельзя |
| Планировщик, EN / UZ | «cctv lens calculator», «kamera kalkulyator», «kamera fokus» — ~10/мес |

| Текущий `/calculator`, 90 дней | 40 кликов / 1 258 показов (RU), запросы — «установка камер … цена». Пересечения с оптикой нет: каннибализации не будет |

**Вывод.** Отдельного поискового спроса на калькулятор оптики почти нет. Ценность инструмента — для продаж и как экспертный материал (ИИ-цитируемость, ссылки, доверие). На поисковый трафик рассчитывать не стоит. Поэтому:
- главный поисковый кластер — «угол обзора / фокусное расстояние камеры» (+ «2.8 мм»), «калькулятор видеонаблюдения»;
- калькулятор HDD/архива сделать частью этапа D (у него свой, тоже малый, спрос);
- из карточек камер со внесёнными углами — блок «угол обзора и дальности DORI для этого объектива» со ссылкой на калькулятор. Это работает на реальный спрос: запросы с артикулом и мм.

## 5. Модель данных оптики (предложение, этап B0)

Новая таблица `camera_optics` (миграция только вперёд, `products` не меняется):

| Поле | Тип | Смысл |
|---|---|---|
| id | uuid | |
| productId | uuid → products.id | Карточка |
| variantKey | string | `2.8mm`, `4mm`, `2.7-13.5mm` — вариант объектива внутри карточки |
| lensType | enum | `fixed` · `varifocal` · `motorized` · `ptz` · `fisheye` · `multi-sensor` |
| fMinMm, fMaxMm | decimal | Для фиксированного объектива fMin = fMax |
| hfovMaxDeg, hfovMinDeg | decimal | Горизонтальный угол: широкий край (fMin) и узкий (fMax) |
| vfovMaxDeg, vfovMinDeg | decimal | То же по вертикали |
| dfovMaxDeg, dfovMinDeg | decimal, null | Если указано |
| widthPx, heightPx | int | Основной поток, максимальный режим |
| sensorFormat | string | `1/2.8"` — только для показа |
| opticalZoom | decimal, null | Для PTZ |
| sourceType | enum | `datasheet` · `product_page` |
| sourceUrl | string | Ссылка на конкретный PDF или страницу производителя |
| sourceCheckedAt | date | |
| verificationStatus | enum | `verified` (две независимые сверки совпали) · `needs_review` · `unsupported` |
| note | text | Расхождения, кроп, режим |

Расчёт по вариофокалу: в положении f ∈ [fMin, fMax] угол интерполируется через эквивалентную ширину сенсора `Sw = 2·fMin·tan(HFOV_max/2)`. Результат помечается «оценка» — кроме двух крайних точек, где угол паспортный.
Fisheye, панорамные и мультисенсорные камеры: `unsupported`, в подборе показываются с пометкой «нужна консультация».

**Порядок проверки — по решению владельца, «все без исключения».** Каждая запись проходит:
1. Datasheet точной модели и суффикса объектива с сайта производителя.
2. Повторное независимое чтение того же datasheet и сравнение с первым.
3. Арифметическая проверка: `2·f·tan(HFOV/2)` и `2·f·tan(VFOV/2)` дают ширину и высоту сенсора с соотношением, совпадающим с `widthPx/heightPx` (±3 %). Сверх допуска — `needs_review` с описанием в `note`.

В подбор идёт только `verified`.

## 6. Решения владельца (10.11.2026)

1. Стандарты найти и сверить самому (выполнено, §3).
2. Этапы — все: A → B0 → B → C → D.
3. Углы обзора по datasheet вношу я; перепроверка всех записей, не выборочная.
4. Карточки с несколькими объективами — выбор варианта внутри калькулятора, карточки не делятся.
5. Выкатка поэтапно: каждый этап — свой коммит и отдельное «да» на деплой.
6. vitest — разрешён как devDependency в `apps/web`.
7. Заявка — существующий `POST /feedback` → CRM, расчёт текстом.
8. Прод-БД — только чтение.
9. Смета D включает монтаж из `calcPricing.PRICE`.
10. Планы объектов обрабатываются только в браузере и на сервер не уходят.
11. Спрос проверить до работы (выполнено, §4).

## 9. Неизвестные, которые закрывает 01-ARCHITECTURE

1. Как сайт пересчитывает USD → сум (источник курса) — для сметы D.
2. Как собрать PDF в браузере: печать или библиотека (вес, лицензия).
3. Правила подбора NVR, PoE и HDD (каналы, бюджет PoE, битрейт → архив) — какие поля для этого есть в каталоге.
4. Куда в админке (`apps/admin`) вывести таблицу `camera_optics` для ручной проверки — или обойтись seed-файлом в репозитории.
