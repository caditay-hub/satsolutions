# satsolutions.uz — полная история работ

Свод по всем рабочим сессиям с 14 мая по 8 сентября 2026 года. Собран 08.09.2026 из 83 файлов рабочей памяти и 31 транскрипта сессий. Документ предназначен для быстрого ввода в курс дела: что за проект, что уже сделано, какие решения приняты и почему, где расставлены грабли.

## Что за проект

**satsolutions.uz** — сайт и каталог компании SAT Solutions (Ташкент, Узбекистан). Компания проектирует, монтирует и обслуживает слаботочные системы: видеонаблюдение, СКУД и турникеты, охранно-пожарную сигнализацию, домофонию, IP-телефонию, СКС и оптику, серверные и ЦОД, шлагбаумы, умный дом, видеостены.

**Технически** это монорепозиторий: Next.js-фронтенд (`apps/web`) и Express/Sequelize-API (`apps/api`) на PostgreSQL, развёрнутые на собственном сервере под PM2. Рядом, отдельным проектом, живёт внутренняя CRM на sats.uz.

**Ключевая особенность — пять полноценных языков**: русский, узбекский, английский, турецкий и китайский. Это не переключатель интерфейса, а полные переводы всего контента, включая описания каждого товара. Требование владельца: любой новый контент выходит сразу на всех пяти языках, без «потом допишем».

### 2. Git-контур и авторизация

- **Локально → GitHub:** SSH-ключ `~/.ssh/id_ed25519_github` (без парольной фразы), `Host github.com` в `~/.ssh/config`, remote переведён с HTTPS на `git@github.com:caditay-hub/satsolutions.git`. Идентичность коммитов: `cadi.tay@gmail.com` / `caditay-hub`.
- **Сервер → GitHub:** отдельный deploy key `/root/.ssh/satweb_deploy` + `/root/.ssh/config`. Remote на сервере расщеплён: **fetch = HTTPS** (анонимно, чтобы `git fetch`/`reset --hard` в деплое работали без ключа), **push = SSH**. Публичный ключ добавлен на GitHub как Deploy key с правом записи. Правка прямо на сервере: `cd /var/www/satweb && git add -A && git commit -m … && git push origin main`.
- **Беспарольный SSH с локальной машины:** алиас `satweb-prod` в `~/.ssh/config` (ключ `~/.ssh/id_ed25519_satweb`, публичная часть в `/root/.ssh/authorized_keys`). Предпочитать `ssh satweb-prod …` вместо пароля.
- **Резервный путь для Windows:** штатные `ssh`/`scp` в Windows требуют интерактива и подвисают в неинтерактивных шеллах. Тогда — PuTTY (`C:\Program Files\PuTTY`): `plink -batch -hostkey <fp> -pw <pw> …`, `pscp -batch -hostkey <fp> -pw <pw> …`; без `-hostkey` plink виснет на подтверждении ключа.
- **Секреты в публичном репозитории.** Репозиторий публичный, поэтому `.gitignore` исключает `.env.server`, `.setup/`, `.secrets/`, `*.tsbuildinfo`. Перед каждым пушем убеждаться, что ни один `.env*` не попал в индекс.
- **Грабля PowerShell 5.1:** `ssh-keygen -N ""` передаёт литеральные две кавычки как парольную фразу, а не пустую строку — ключи генерировать из Git Bash.
- **Расхождение веток кода.** Деплой делает `git reset --hard origin/main` (предварительно стешируя), поэтому: всегда коммитить и пушить до деплоя и не править одни и те же файлы одновременно локально и на сервере.

### 3. Деплой

Деплой **ручной, «по кнопке»** (не по пушу — сознательно, потому что нет ни стейджинга, ни тестов).

- Локально: `npm run deploy` → `ssh satweb-prod "bash /root/deploy-satweb.sh"`.
- На самом сервере: `bash /root/deploy-satweb.sh` напрямую.
- Канонический исходник скрипта в репозитории — `scripts/deploy.sh`; синхронизация на сервер — `npm run deploy:push-script` (либо `scp scripts/deploy.sh satweb-prod:/root/deploy-satweb.sh`). Бэкапы предыдущих версий на сервере — `/root/deploy-satweb.sh.bak.*`. Мёртвый дубль `scripts/deploy-satweb.sh` (со старым опасным globом) удалён — канон один.

**Что делает скрипт:** стешит прямые правки на сервере («auto-backup», автоматически подрезая старые стеши до 3) → `git reset --hard origin/main` → `npm install --include=dev` → `npm run build` (обёрнут в `timeout 420` + один ретрай `build_once`) → `pm2 restart sat-api sat-web sat-admin --update-env` → **шаг 6**: удаление устаревших ISR-пререндеров каталога и прогрев страниц curl'ом по локалям.

#### Грабли деплоя (все проверены на боевых инцидентах)

1. **`npm run deploy` запускается только локально.** Алиас `satweb-prod` живёт в локальном `~/.ssh/config`; на сервере команда даст `Could not resolve hostname satweb-prod`.
2. **Коммита мало — нужен `git push`.** Сервер тянет код с GitHub, незапушенный коммит просто не доезжает: деплой отрабатывает «успешно», PM2 рестартует, а собирается СТАРАЯ версия. Коварный симптом контентных партий: русский текст идёт напрямую в БД и обновляется, а локали из `productI18n.json` — нет, и это выглядит как «uz/en/tr/zh не подхватили перевод». Проверка перед деплоем — `git status -sb` без `ahead`; проверка после — `ssh satweb-prod 'cd /var/www/satweb && git log --oneline -1'` должен показать именно ваш коммит (на «DONE» в логе не полагаться). Грабля срабатывала минимум дважды (21.08 и 07.09.2026).
3. **Tracked-файлы нельзя править прямо на сервере** — их снесёт `git reset --hard`. Особо критично для `apps/web/src/data/productI18n.json`: статический импорт всё равно требует пересборки, так что правка на сервере и невидима, и потеряна. Порядок: локально → commit → push → deploy. Данные не из git (фото в `uploads/`, содержимое БД) на сервере менять можно.
4. **Параллельный деплой молча пропускается.** При уже идущем деплое `npm run deploy` **выходит с кодом 0**, напечатав только «!! деплой уже идёт» — выглядит как успех, но ничего не выкатывает (реальный случай 04.09.2026). Смотреть в хвост вывода строку `==> [satweb deploy] DONE <дата>`. Ждать чужой деплой по логу `/root/deploy-last.log` (`grep DONE`); **`pgrep -f deploy-satweb.sh` через ssh всегда находит сам себя** (шаблон есть в строке запуска удалённой команды) — цикл ожидания на нём не завершается никогда, использовать `pgrep -f 'bash /root/deploy-satweb.sh'`.
5. **Глоб очистки ISR: `other.*`, а не `other*`.** Паттерн `-path '*/catalog/other*'` матчил и `catalog/other/page.js` внутри папки роута → `MODULE_NOT_FOUND` → **500** на `/catalog/other` во всех локалях и цикл рестартов `sat-web`. Правило общего вида: чистить ISR только по `<route>.<ext>` или явным именам `*.html/.rsc/.meta/.body`, никогда по префиксу имени папки — генерируемые `page.js`, `*_client-reference-manifest.js`, `*.nft.json` лежат ВНУТРИ папки роута, а пререндеры — сиблинги рядом.
6. **`pm2 reload` не годится.** В fork-режиме reload надёжно перезапускал только `sat-api`, а `sat-web`/`sat-admin` подвисали и продолжали отдавать старый ISR. Заменено на `pm2 restart … --update-env`. Если фронт всё же не обновился — `ssh satweb-prod "pm2 restart sat-web sat-admin"` и подождать ревалидацию (у каталога `revalidate=300`).
7. **Полу-собранный билд + процесс на старом манифесте** — самый тяжёлый инцидент (22.08.2026, ~8,5 ч сломанного сайта). Симптом: все страницы отдают 200, но у посетителей нет CSS и сыплется `ChunkLoadError` — HTML ссылается на хеши, которых нет на диске, nginx отдаёт по ним 400 с MIME `text/html`. Причина: `next build` был убит на самом конце (пропал только `prerender-manifest.json`), `pm2 restart` не отработал, процесс крутился со старым билдом в памяти, а ISR дописывал `.html`/`.rsc` с мёртвыми ссылками. Корень — код возврата `build_once` после ретрая не проверялся, и рестарт выполнялся даже после провальной сборки. Диагностика тремя командами: сверить `curl … | grep -o '/_next/static/css/[a-z0-9]*\.css'` с `ls .next/static/css/`; проверить наличие `.next/prerender-manifest.json` (без него `next start` падает в 502 с ENOENT в `pm2 logs sat-web`); сравнить время старта `sat-web` в `pm2 jlist` с mtime `.next/BUILD_ID`. Лечение — полный `npm run build` на сервере (без `timeout`) и `pm2 restart sat-api sat-web sat-admin`. **Мониторинг по кодам ответа такое не ловит** — проверять именно доступность CSS/JS-хешей.
8. **Зависание `next build` (26.06.2026, 16 минут при пустой нагрузке).** Причина — `next/font/google` тянул шрифты из сети на КАЖДОЙ сборке (`npm run clean` сносит кэш), и фетч застревал. Исправлено переводом на self-hosted `@fontsource-variable/{jura,inter,caveat}` (импорт `/wght.css` в layout, woff2 в бандле — сборка в сеть не ходит) плюс `timeout 420` с ретраем. Шрифты сайта: заголовки/бренд — Jura, тело/UI — Inter, акцент — Caveat. Диагностика зависания: `ssh satweb-prod 'pgrep -af "next build"; ps -eo pid,etimes,cmd | grep "next build"'`.
9. **Данные API отстают в статике на один деплой.** Sitemap и пререндеры пекутся во время билда против ещё СТАРОГО API (порядок шагов: build → restart api). Для sitemap поставлен `revalidate 3600`; для остального помнить: изменения API видны в SSG либо после второго деплоя, либо после ревалидации.
10. **cwd в Bash-сессии персистит между вызовами** (укусило трижды за 28–29.08). Цепочка `cd apps/web && npx tsc …; git add apps/web/…` выполняет `git add` уже из `apps/web` → `fatal: pathspec … did not match`, exit 128, и деплой в той же цепочке не стартует. Правило: `git add/commit/push/deploy` — отдельным вызовом из корня либо начинать с `cd /d/sat_web_github && …`; проверку tsc заканчивать `; cd /d/sat_web_github`.

### 4. Запись данных в прод без админки

Безопасный способ — **одноразовый seed-скрипт на моделях приложения**, чтобы не выгружать креды наружу.

- **Файлы (uploads):** `/var/www/satweb/apps/api/uploads/` с подпапками `portfolio/` (обложки `<slug>-cover.jpg`), `images/` (галерея `*.webp`), `brands/` (лого `*.png`). Отдаются по `https://api.satsolutions.uz/uploads/...`. Заливка — `scp <файл> satweb-prod:<путь>`.
- **БД:** написать `apps/api/src/seed-<name>.ts` по образцу `seed.ts` (`import "dotenv/config"; initModels(); await connectDb();`, импорты с расширением `.js`), обязательно **идемпотентно** (findOne по slug → update/create). Запуск: скопировать скрипт в `apps/api/src/` и `ssh satweb-prod 'cd /var/www/satweb/apps/api && npx tsx src/seed-<name>.ts'` (`.env` подхватывается из cwd, `tsx` есть в devDependencies).
- **После прогона скрипт с сервера удалить** (`rm`) — untracked-файл блокирует git-операции при следующем деплое; в репозиторий его при этом закоммитить.
- **ISR:** новые slug портфолио рендерятся on-demand (`dynamicParams`), деплой не нужен; секции с ISR (главная, каталог) обновятся в пределах `revalidate=300` либо после деплоя.

### 6. Защита сервера: анти-скрейпинг, лимиты, fail2ban

Настроено 03.07.2026 и существенно пересмотрено 22.08.2026. Всё живёт **только на сервере, не в git**: `/etc/nginx/conf.d/antiscrape.conf` + vhost `/etc/nginx/sites-enabled/satsolutions`; копии — `/root/nginx-configs-backup/` и `/root/nginx-satsolutions.bak.*` (старые `.bak`-дубли вынесены из `sites-enabled` в `/root/nginx-old`, они давали conflicting server name).

Что действует:

- **Фильтр ботов по User-Agent** (`map $bad_bot` → 403): python-requests, scrapy, aiohttp, go-http-client, **curl/wget**, пустой UA, SEO-краулеры (mj12, petal, semrush, ahrefs, bytespider…), а также безымянный `Mozilla/5.0 (compatible; crawler)`. Googlebot, Bingbot, Yandex — не тронуты.
- **Rate limit.** Зоны: `web` 10 r/s, `api` 8 r/s, `uploads` 30 r/s. Первоначальный `burst=50` на HTML душил живых людей, а не ботов: замер суточного лога показал у настоящих браузеров пики 96/51/34/32 запроса в секунду (HTTP/2 шлёт страницу залпом), и 429 за четверо суток получали ТОЛЬКО реальные Chrome — ни одного скрейпера. Исправления: `burst` поднят до 150; статика `/_next/static/` и `/_next/image` выведена из-под лимита через `map $request_uri $rl_key` с пустым ключом.
- **Фото товаров** `/uploads/` раньше были без лимита — один адрес выкачал за сутки 840 фото с пиком 268/сек. Введена зона `uploads` 30 r/s burst=60: человек тянет 16–17 картинок/сек и не замечает, массовая выкачка замедляется почти в 10 раз. ⚠️ Собственный оптимизатор картинок Next ходит к API с ВНЕШНЕГО адреса сервера (843 запроса/сут, пик 28/сек) — он выведен из-под лимита через `geo $uploads_free`, иначе задушило бы картинки всего сайта.
- **Хотлинк-защита:** `map $http_referer $foreign_referer` → 403 при чужом домене. **Пустой Referer разрешён намеренно** — так ходят Googlebot-Image, GoogleOther (фид Merchant), YandexImages, YandexMarket, bingbot и собственный node-оптимизатор; запрет пустого сломал бы индексацию картинок и Shopping.
- **fail2ban**, 3 jail с bantime 1 час: `sshd`, `nginx-botsearch` и кастомный `nginx-scan` (`/etc/fail2ban/filter.d/nginx-scan.conf` — пробы `.env`, `.git`, `wp-login`, `phpmyadmin`; бан после 3 попыток).
- **`robots.txt` отдаётся статикой nginx** (`location = /robots.txt` → `/var/www/satweb-static/robots.txt`). Причина: 30.06–01.07 короткие 502 при рестартах деплоя пришлись в том числе на `robots.txt`, а когда robots отдаёт 5xx, Google помечает ошибкой всю очередь обхода — в GSC вылезло «Ошибка сервера (5xx): 331 страница» из пары минут даунтайма. Теперь robots переживает любые рестарты Next. При изменении правил править ФАЙЛ на сервере (и `apps/web/public` — для консистентности исходника).

⚠️ Два предупреждения, которые стоят потерянных часов:

- **Голый `curl https://satsolutions.uz/...` получает 403.** При любых проверках сайта добавлять `-A "Mozilla/5.0 …"`. Внутренние проверки с сервера на `localhost:3000/4005` идут мимо nginx и работают как раньше (прогрев в деплое — тоже).
- **`systemctl reload nginx` на этом сервере НЕ подхватывает конфиг**: рапортует SUCCESS, но воркеры остаются старыми (видно по `ps -eo pid,lstart`). Нужен `systemctl restart nginx`. Признак работы старого конфига — строка `excess: 50.x` вместо нового порога в `/var/log/nginx/error.log`.

Отдельно: **водяные знаки на фото товаров ставить нельзя** — политика Google Merchant Center запрещает вотермарки и рекламные наложения, это убьёт Shopping.

Если когда-нибудь включат прокси Cloudflare — обязательно сначала настроить real-IP в nginx (`set_real_ip_from` для диапазонов CF + `CF-Connecting-IP`), иначе анти-скрейпинг увидит всех посетителей как несколько IP Cloudflare и задушит сайт.

### 1. Таксономия и структура каталога

- Слияние сделано переименованием категорий в БД **по имени**, а не по id: `UPDATE categories SET name=target WHERE name=source AND id IN (есть опубл. товары)`.

### 2. Фасетный фильтр

**Единый фильтр на всех страницах каталога (24.06.2026).** Раньше был «новый» сломанный фильтр на страницах типа и «старый» на `/products` — оставлен один.

- **Бэкенд `/product-facets`** (`apps/api/src/routes/public.ts`), scope-aware: принимает `{type, brand, category, q, chars, priceMin, priceMax}`, возвращает `{brands, types, price, chars}`.
- **Drill-down:** счётчик каждого фасета считается с учётом ВСЕХ остальных активных фильтров, КРОМЕ своего измерения (`cond({brand:false})` и т.п.). Поэтому любой показанный вариант кликабелен и всегда даёт >0 — пустую комбинацию собрать нельзя. Char-фасеты появляются только при ровно одном выбранном типе (`typeNames.length===1`).
- **Токенизация характеристик — `charTokensSql()`**, общий хелпер: срез скобок `(...)` + split по запятой. Применяется в трёх местах одинаково: генерация фасетов, фильтр `/products`, drill-down `charsExists`. ⚠️ Если реализации разойдутся — счётчик фасета ≠ выдача (был баг: «до 300m (PoE)» фасет считал 26, фильтр давал 19).
- **Лимиты (best-practice 3–6 групп):** char-групп максимум **6** (`MAX_GROUPS`), значений в группе **10** (`MAX_VALUES`). Ранжирование групп по «качеству» = `total/√(distinct)` (штраф за кардинальность). Глушение шума: drop если distinct>14, либо distinct>8 при avg<1.6.
- **Нормализация значений — `charNormSql`:** схлопывает дефис/тильду (RS-485 = RS485) и удаляет ВСЕ пробелы (с 07.07: «Micro SD до 512 GB» = «microSD до 512GB»). ⚠️ Слэш НЕ трогаем — сломает «10/100/1000». `charNormSql` общий для фасетов и фильтра, поэтому счётчики согласованы.
- **Сортировка значений** (фикс 06.07): не `localeCompare` (давал «12TB, 1TB, 500GB»), а `facetValueCmp` в public.ts — числовые по возрастанию с распознаванием единиц (тб/tb→1e12, гб/gb→1e9, мб, кб, км), нечисловые по алфавиту перед числовыми.

### 3. Поиск по каталогу

Реализация — `apps/api/src/routes/smartSearch.ts`, два эндпоинта:
- **`/search-suggest`** — мгновенный дропдаун в шапке (`SiteHeaderClient.tsx` → `getSearchSuggest`). Быстрый ILIKE по `p.name` / `p.modelCode`, **без ИИ** (нельзя дёргать модель на каждый keystroke).
- **`/search-smart`** — полный поиск (Enter → `/products?q=`). Сначала `directSearch` (ILIKE по name/model), и если «сильных» совпадений < 12 — вызывается Claude (`claude-haiku-4-5`) как маршрутизатор: узбекский/английский/сленг → `category_slugs` + RU-keywords, дальше `mappingSearch`. Кэш маппинга — таблица `smart_search_cache`.

**Ключевой факт архитектуры:** имена товаров в БД **только на русском**. Локализованные имена (uz/en/tr/zh) живут в `apps/web/src/data/productI18n.json` (ключ = UUID товара, ~3064 записи), в БД их нет.

**Фикс локализованного поиска (30.06, 17cc225).** Узбекские/английские запросы («abonent terminali») давали 0. Добавлен `apps/api/src/lib/productI18nIndex.ts`: грузит productI18n.json в память (путь через `import.meta.url`, TTL-перезагрузка 5 мин, индексирует name+shortDescription всех локалей), `matchI18nProductIds(q)` → id товаров. Подключён в `/search-suggest` и в `directSearch` через `OR p.id IN (:ids)`; локализованные совпадения считаются «сильными». Источник правды тот же JSON, без миграций и дублирования.

**⚠️ Критичный фикс + раскладка (01.07).** Поиск был СЛОМАН для запросов без i18n-совпадений (например, русское «пожарка»): при пустом i18n-индексе подставлялся sentinel `[""]`, а `p.id` — UUID → `p.id IN ('')` роняло каст (`invalid input syntax for type uuid`) → падал весь directSearch/suggest → 0 результатов. Фикс: sentinel `[""]` → `NIL_UUID` (`00000000-...`). Тогда же добавлена **обработка раскладки клавиатуры** (`flipLayout` RU↔EN по позиции клавиш): «gj;fhrf» = пожарка, «вфргф» = dahua. `flipLayout` вынесен в общий util `apps/api/src/lib/kbLayout.ts` и работает во ВСЕХ 4 точках: suggest, `getProducts` (public.ts), `directSearch`/Claude (smartSearch.ts) и `/product-facets` (иначе чипы категорий не появлялись на флип-запросах).

**⚠️ NB деплоя API:** sat-api крутится из `dist/` (`node dist/index.js`), НЕ через tsx. Деплой правок API = git pull + `npm run build` (`tsc --noCheck`) + `pm2 restart sat-api`, иначе dist протухает.

**Релевантность (01.07).** Запрос «датчик» выдавал КАМЕРЫ (у камер «PIR датчик» в описании) — три пути поиска матчили `shortDescription`. Матч по `shortDescription` убран из `getProducts` и `directSearch`; осталось имя/модель/категория/бренд/локализация/раскладка. Результат: «датчик» 83→55, камер 10+→3. Побочный эффект: атрибутивные запросы (poe/ip67) больше не ловятся по описанию — для них фасеты. Семантику (датчик→извещатели) даёт Claude в `/search-smart`. Добавлены **чипы категорий** сверху выдачи и для обычного поиска (не только smart) из `typeFacets.types`.

**Опечатки (01.07):** «подарка»→0. В system-промпт `askClaude` добавлено «исправляй опечатки/раскладку, даже обычное слово в контексте безопасности трактуй как ближайший термин». ⚠️ Кэш чистить при правках промпта (`DELETE FROM smart_search_cache WHERE query=…`), иначе старый пустой маппинг залипает.

**Токенный матч (14.07, c06b3b1).** Запрос «Беспроводной замок GL300W» → 0, потому что искалась вся фраза одним куском, а товар назывался «Беспроводной замок **ZKTeco** GL300W» — лишнее слово внутри рвёт непрерывную подстроку. Бэкап первой волны: `products_chars_bak_20260717`. Откат: `UPDATE products p SET characteristics=b.characteristics FROM products_chars_bak_20260717 b WHERE b.id=p.id;`

**Вторая волна (07.09.2026): «тонкие» характеристики добиты.** 1100 товаров с 1–2 ключами доведены до полных; **среднее по каталогу — 5.0 ключей**, тонких осталось 173 (законный минимум: HDMI-кабели, штекеры, расходники). Бэкап `products_chars_bak_20260907`. Метод двухслойный:
1. Коммутаторы (105) и кронштейны/аксессуары (185) — прочитаны описания, патчи вручную (`patch_switches.json`, `patch_access.json`), только явные факты (L2/L3, PoE, порты, бюджеты, стандарты 802.3af/at/bt).
2. Остальные 810 — **парсеры из имён** с ручным контролем превью (`parse_cabinets/optics/sfp/ups/batch2/final.py`), потому что имена наши и структурные: шкафы NU + ШхГхВ, SFP скорость/дальность/волна, PLC 1×N, HDD объём/форм-фактор, Dahua NVR (код = серия + HDD + каналы).

Заливка: `apply_chars.py` (jsonb `||` merge, транзакция). **Грабли:** NBSP (`\u00A0`) в именах товаров ломает матчинг — нормализовать; cp1251-консоль Windows — запускать `python -X utf8`; `chmod 644` на /tmp-файл, иначе psql выдаёт Permission denied.

**Механика применения (обе волны):** выгрузка категории в JSON через `psql \o` → форматирование node → чтение → авторский `<cat>_chars.json` (id→chars) → генерация `UPDATE products SET characteristics='...'::jsonb WHERE id=...` → scp → `psql -f`. ⚠️ Кириллица в WHERE через ssh ломается — фильтровать по ASCII/id. **Витрина обновляется по ISR ~10 минут, code-деплой не нужен — это данные, а не код.**

**Перевод описаний ЗАВЕРШЁН 100%: 3063/3063 товара на uz/en/tr/zh** (коммит 790f074, 30.06.2026). Поле `description` — длинный markdown с секциями `## `, списками `- `, блоком `## FAQ` с `Q:`/`A:`.

### 7. Фотографии товаров

**⭐ Итоговое правило (27.08.2026, после четырёх кругов правок владельца).** Все фото каталога выровнены **по площади объекта**: `sqrt(Ш*В) = 66%` кадра, потолок стороны **86%**, фон белый, WebP q88, кадр квадратный 1200×1200. Скрипт `/root/apply_uniform.py` (`--apply` = с бэкапом). Применено ко всему каталогу: обработано 3153 из 3511 фото, бэкап `/root/photo_bak_20260827_size/` (65 МБ). Итог: «вес» у 90% товаров ровно 66 (было 30–95), ни одно фото не упирается в край. Длинные предметы (DAC-кабели, патчкорды) остаются 36–48 — упираются в потолок по ширине, это физика, не ошибка.

**Путь к правилу (что НЕ сработало):** (1) равнять по большей стороне 86% → вытянутые предметы кажутся мельче квадратных; (2) площадь 74% + потолок 94% → «некоторые слишком большие»; (3) «трогать только выбросы ≥95%» → в сетке каталога разнобой остался виден. **Показывать результат надо СЕТКОЙ каталога, а не отдельными фото — по одному кадру решение не принимается.**

**⛔ Чёрный фон запрещён (владелец, 27.08): «чёрный фон не надо».** Проверка перед публикацией: яркость 4 углов; если < 128 — фото не публиковать (искать вариант на белом). У itmag часть кадров именно на чёрном — отсеивать.

**⛔⛔ Никогда не ставить одинаковые фото в одну карточку.** Владелец указывал на это трижды за 27.08 (QSFP-DAC, R3-MS-E, С2000-КДЛ). Причина повторов всегда одна: при заливке один и тот же кадр идёт и в обложку, и в галерею, либо сайт производителя отдаёт один снимок в нескольких размерах.

**Детектор дублей — три признака, достаточно любого** (двух не хватало, владелец нашёл пропущенный дубль на С2000-КДЛ):
1. dHash ≤ 8;
2. силуэт объекта < 0.06;
3. кадр целиком (64×64, autocontrast) MAD < 14 И вырезанный по bbox объект MAD < 35.

⚠️ Признак (2) НЕ работает для белого предмета на белом фоне (маска нестабильна) — именно так и проскочил С2000-КДЛ (хэш 11, силуэт 0.906, хотя кадр тот же); ловит его признак (3). Победитель в группе выбирается по `резкость × (размер/1200)` — крупный файл выигрывает у мелкого того же кадра (так уходят старые 800px-обложки с чужими вотермарками, например «ЭТМ» на С2000-КДЛ). #### 8.4. Правила, чтобы обновление цен не ломалось

1. **Формула зафиксирована** (см. 8.1), округление только вниз (в истории было смешанное).
2. **Один товар — один поставщик.** Цену товара обновляет ТОЛЬКО файл его поставщика. MikroTik ≠ Hikvision-прайс, даже если позиция там встречается.
3. **Порог автоприменения ±40%.** Больше — только руками (5-pack упаковки, смена поколения, смена поставщика).
4. **Бэкап перед каждым применением:** `products_price_bak_<дата>`.
5. **Курс 12500 в одном месте**; менять при смене курса поставщика.
6. **Generic-имена сверять только вместе с ценой.** «Набор Инструментов» Hikvision $20 ≠ NIM-25 ВОЛС 9,5 млн Pixietech — `supplierCode` обязан включать поставщика.

#### 8.6. Грабли матчинга артикулов (собраны болью)

- **Сайт правил названия** относительно прайса: убраны «(O-STD)», «(C)», объективы; Рубеж переименован в полные русские названия; кириллица→латиница (R3-МС→R3-MS); артикулы поставщика (A17, (19)) на сайте отсутствуют.
- **Мягкий скоринг без жёсткого правила «все цифро-токены совпали» даёт ложные пары** (cat-6 → cat-5). Правильная формула: все кодовые токены обязаны совпасть (с чисткой пунктуации и числами-с-границами) + цена ±10% как арбитр. Совпадение кода И цены всё равно может врать (OTDR FL_1600 ~ шкаф …*1600) — последние ~60 пар только глазами. Итог сверки 27.08: **1679 из 1795 (94%)** сопоставлено 7-ступенчатым матчером.
- **Похожие коды НЕ склеивать:** G2 ≠ G2H ≠ G3, -S ≠ -B, LIU ≠ LIUF, K1 ≠ K1/VPro.
- **Длины кабелей:** «1,5m» и «15m» / «15M» схлопываются в один артикул — 15-метровый OM4 получил цену полутораметрового (78 190 вместо 190 900). Проверять привязку по длине отдельно. Тот же корень у `pro-hdmi-4k-15m` (25 690 = цена кабеля 1,5 м).
- **Кириллическое «ММ»** в артикулах (PXT-PC-LC/UPC-SC/UPC-ММ-*) матчилось на латинские SM-двойники и получало их цены.

### 14. Отзывы о товарах

Нативная система оценок и отзывов внедрена 17.07.2026. Отзыв публикуется **только после модерации**. ⚠️ **Отзывы не фабриковать** — только реальные (политика Google + честность). Автозаливка в Google невозможна (Google принимает отзывы лишь от аккаунта клиента); звёзды компании в самой выдаче Google — только через GBP, не через site-разметку (self-serving Organization reviews не показываются с 2019).

**Backend (apps/api):** миграция `051-reviews.ts` + модель `Review.ts` (rating / authorName / text / status [PENDING|APPROVED|HIDDEN] / serviceKey / meta); миграция `052` добавила `productId`. Роуты: публичные `POST /reviews` (→PENDING, антиспам ≤3/IP/сутки) и `GET /reviews[?serviceKey=|?productId=]` (только APPROVED + avg/count); админские `GET/PATCH/DELETE /admin/reviews` (auth ADMIN/EDITOR).

**Frontend:** `ReviewForm.tsx` (звёзды + текст + имя), `ReviewsSection.tsx` (агрегат + карточки), страница `app/[locale]/reviews/page.tsx`. **Товарные отзывы:** на `/products/[slug]` — виджет «Оцените товар» (productId), список, компактный рейтинг и **`aggregateRating` в Product JSON-LD только при count>0** — легальный путь к звёздам товара в выдаче Google. Виджет стоит на ВСЕХ published-товарах (рейтинг и схема появляются только при наличии отзывов).

**Модерация:** `apps/admin/src/app/reviews/page.tsx` → `admin.satsolutions.uz/reviews` (вкладки Новые/Одобренные/Скрытые/Все).

**Статус:** страница `/reviews` не в футере/меню и стоит `noindex` — включать, когда наберутся реальные отзывы. Мелкий недокрут: заголовок `ReviewForm` жёстко «Оцените нашу работу», на товаре стоило бы «Оцените товар». Ручное одобрение в БД: `ssh satweb-prod`, DATABASE_URL из `/var/www/satweb/apps/api/.env`, `PGCLIENTENCODING=UTF8 psql` — ⚠️ кириллица в WHERE ломается, фильтровать по ASCII/status.

## Контент, i18n и SEO

### 1. Языковая стратегия: пять полноценных языков

Сайт satsolutions.uz — Next.js + next-intl, локали **ru / uz / en / tr / zh**. Базовая локаль — `ru` без префикса (`localePrefix: as-needed`), поэтому `/ru` отдаёт 307 → `/`, и индексируется именно корень.

Ключевое решение принято 24.06.2026 и с тех пор ужесточалось:

- Изначально tr/zh планировались как фолбэк на английский. **Отменено:** цель — пять полноценных языков, всё под SEO.
- **⚠️ Правило владельца от 20.08.2026** (повторено дважды, второй раз с восклицаниями: «у нас сайт на 5 языках!!!»): **любой новый контент — блог, услуги, товары, лендинги — пишется сразу на всех пяти языках.** «tr/zh потом» больше не вариант. Антипример из истории: волна статей `narxlari` делалась в три захода (ru+uz → en → tr+zh) вместо одного.
- Автоопределение языка в middleware: `Accept-Language: uz` → 307 на `/uz` (боты и cookie `NEXT_LOCALE` исключены). Решение владельца «аудитория узбекская». **Дефолтную локаль при этом не меняли:** RU-спрос 2230/мес против UZ 600/мес, 96% кликов приходит с ru-страниц.
- ⚠️ **Узбекские URL в Google Ads запрещены окончательно** — объявления на `/uz/` получали DISAPPROVED; узбекские запросы ведут на русские посадочные.

#### Локализованная 404

**Локализованная 404 на 5 языков живёт в рутовом `apps/web/src/app/not-found.tsx`, не в `[locale]/not-found.tsx`.** В связке next-intl, где `<html>` рендерится в `[locale]/layout.tsx` и **рутового `app/layout.tsx` нет**, `notFound()` из страниц под `[locale]` не перехватывается локальным not-found — всплывает выше, и Next показывал встроенную «404: This page could not be found».

Что **не** работает (проверено, не повторять): `useTranslations`/`getTranslations` в not-found (серверный i18n-контекст при `notFound()` недоступен); `res.headers.set('x-pathname')` в middleware (это response-заголовок, `headers()` в RSC читает request-заголовки).

Рабочее: рутовый `not-found.tsx` — **клиентский** (`"use client"`), рендерит свой `<html>/<body>`, локаль берёт из `usePathname()`, тексты из инлайн-словаря без i18n-зависимостей. **Фикс «ложных 404» 10.08** (GSC ругался: несуществующие `/products/<slug>` отдавали 200). Две причины:
1. `app/[locale]/products/loading.tsx` включал streaming для **всего** сегмента, включая `[slug]` — статус 200 уходил с шеллом до `notFound()`. Loading перенесён в `products/group/`, а поиск `/products` получил Suspense-скелетон внутри `page.tsx`.
2. `generateMetadata` карточки глотал 404 (catch → fallback title) — теперь `notFound()` и в метаданных.
⚠️ `notFound()` / `permanentRedirect` бросают спец-исключения — в catch проверять `(e.digest||'').startsWith('NEXT_')` и пробрасывать, иначе catch их съест.
**Урок: segment-level `loading.tsx` = streaming = замороженный статус 200 для вложенных страниц.**

## Правила работы, выведенные практикой

Это не пожелания, а условия, нарушение которых уже приводило к потерям времени или денег.

### Деньги и внешние сервисы
1. **Платные API** (Anthropic, fal и прочие) — только с явного разрешения на конкретный запуск, с озвученной стоимостью. По умолчанию всё делается своими силами.
2. **Прод, реклама, деньги** — никаких изменений без явного «да» на конкретное действие. Вопрос владельца не равен согласию: «а можно ли?» — это вопрос, а не команда.
3. **Запуск кампаний, повышение бюджетов, смена стратегии ставок** — подготовить, показать цифры, спросить. Никогда не включать самому.
4. **Не проводить реальные выплаты** и не отправлять рассылки живым клиентам.

### Контент
5. **Пять языков всегда.** Любой новый контент выходит сразу на ru/uz/en/tr/zh. Формулировка владельца: никаких «tr и zh потом».
6. **Любое изменение товара** — обновить переводы в `productI18n.json` и `seoTitle`/`seoDescription`.
7. **Любое изменение сайта** — с учётом SEO: slug и редиректы, canonical и hreflang, sitemap, семантика.
8. **Тексты — глубоко и красиво.** Лонгриды от шести абзацев, профессиональный стиль, самопроверка всех текстов без исключений. Штампы вроде «идеальный» и «в современном мире» не проходят.
9. **Фотографии** — единый масштаб: квадрат 1200, объект 86% кадра, WebP 88. Прогонять через `normalize_photo.py` ДО заливки. Галереи из внешних источников — только после согласования эталона.

### Аналитика и реклама
10. **Аудит только исчерпывающий**, не выборочный. Каждое слово, каждая кампания, каждая настройка плюс живая выдача.
11. **Рекомендация подаётся доведённой до конца.** Противоречие в данных означает смену вывода, а не «подтверждена с уточнением». Если что-то не изучено — так и сказать.
12. **Не выдумывать правки к тому, что объективно в порядке.** Проверено на группе «B2B — гостиницы»: и объявление, и посадочная были хороши, низкая оценка оказалась устаревшей статистикой.
13. **Проверять данные, а не доверять названиям полей.** Дважды за одну неделю выводы переворачивались: клики по Telegram считались вторичными, но управляли ставками; «98 товаров без цены» оказались артефактом чужого источника данных.

### Технические привычки
14. **Деплой:** коммит → `git push` → `npm run deploy` из корня. Без push сервер выкатит предыдущий коммит и отрапортует об успехе. Проверка: `ssh satweb-prod 'cd /var/www/satweb && git log --oneline -1'`.
15. **Скрипты-правки** — с сухим прогоном по умолчанию и записью только по флагу `--apply`, с встроенной валидацией лимитов.
16. **Параллельные агенты** — каждому своя подпапка или префикс файлов, иначе затирают работу друг друга.
17. **Проверка текста на странице** — питоном, а не связкой `sed` и `grep`: она даёт ложные нули на многословных фразах.
